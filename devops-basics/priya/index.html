Pilot first: Starter Bank

Before I hand a team repository to a cohort, I run it with my trainers. Three of us built a small site through pull requests. Then I wrote the guide for a mixed Sec 1 to 3 CCA group.

I'm Priya. I plan courses for a team of trainers. My question for this brief: could every trainer on my team run it? With any group, on a school network?

So I made choices for the team, not for one expert. Everything happens in the GitHub website. Nobody installs anything or learns a second editor. The deploy workflow is GitHub's own Static HTML starter. I only updated its action versions. The only gate is a human one: a ruleset that needs one approval on every pull request.

Stops on the mapThe four deliverables

  1. team-site-templateThe template repository. Starter pages that open straight away and a README with 3 tasks. Also an issue template and a review checklist. Every file is shown, with a zip.
  2. Starter Bank, the live siteThree 5-minute paper starters for Git lessons, written by the pilot team. It is the site as we left it after the last merge.
  3. 5 merged pull requests, #4 to #8Each with its diff and review. One broke a link on the live site. One had a conflict.
  4. The 1-page class guideFor a CCA group of Sec 1 to 3 students. Team rules, and a plan for students who are still 12.

The two trainers, our account names and our review comments are made up, like me. The Git history is real. I made every branch, commit, conflict and merge in Git. The diffs come from that history.

We met for two afternoon sessions. Each of us took one issue: write one 5-minute starter for a Git lesson. A starter had to need only paper. Then it still works when the devices won't log in.

  1. harbour-trainer wrote "Commit or not?", a card sort of good and bad commit messages.
  2. pine-trainer wrote "Spot the conflict", two sticky notes and one sentence.
  3. plan-lead (me) wrote "Who can see it?", about what a public repository shows.
  4. pine-trainer then did task 3 for the team: renaming the site from "Our team site" to Starter Bank.

Two things happened that I wanted the guide to plan for. My branch and pine-trainer's both added a line in the same place. GitHub showed a conflict. I fixed it in the browser. And the link in #5 said spot-conflict.html when the file was spot-the-conflict.html. I approved it without clicking it. It went live broken. harbour-trainer found it on a phone the next day. Pull request #7 fixed it.

The review checklist already said "Every link on the page works". I had it open and skipped that line. A checklist depends on people reading it. I come back to that below.

Why these choicesBuilt for a team of trainers

  • The GitHub website only. The pencil edits a file. "Commit changes" lets you make a new branch, then "Propose changes" opens the pull request. One tool means one set of screenshots for my trainers.
  • The starter workflow, almost unchanged. In Settings, Pages, a trainer picks GitHub Actions. The template already holds GitHub's Static HTML workflow. GitHub's copy still names action versions that run on Node 20. GitHub has moved its runners off Node 20. So I changed three version numbers and nothing else. If it breaks, GitHub's own docs still match it step for step.
  • A ruleset with one rule. "Require a pull request before merging", with 1 approval. The author can't approve their own. Rulesets are free on public repositories with GitHub Free.
  • Public repositories. GitHub Pages on a free account needs one. So the site and the history are public. The rules on names and emails matter more.
  • Template, not fork. A repository made from a template starts with one commit. Students get a clean start and none of my history.

I left out an automated check on purpose. It would mean one more file that only some trainers can fix. The broken link in #7 is the cost of that choice.

RubricHow it measures up

  • Every change went through a pull requestMain has 6 commits: the template's first commit and 5 squash merges, #4 to #8. The ruleset blocked direct pushes. See the history.
  • Site deploys automatically and worksEvery merge ran the Pages workflow. The live site works now. For a while it had a dead link, because nothing but a person checked it.
  • No keys or personal data in codeNo keys exist in this project. Account names are made up. The checklist asks the reviewer to look for names, emails and photos. "Who can see it?" teaches the reason.
  • Guide fits your students' agesThe guide checks ages first. Most Sec 1 students turn 13 during the year. So it gives the under-13s a real role without an account.

What I would changeWhere the plan is thin

My pilot was three adults. The timings in the guide are my best guess for 13-year-olds, not something I watched. A first pull request took each of us about 20 minutes. I have doubled that for students. One real session with a class would tell me more than my spreadsheet.

The review checklist is also only as good as the reviewer. I approved a dead link with the checklist in front of me. For a cohort, I'd ask a colleague like Rajan to add a link check. Then a person checks the words, and a script checks the links.
