Stall Board: a team site that only ships green

Four Sec 3 students build a canteen menu site in one repository. Nothing reaches main without a pull request, a passing check and a teammate's approval. Then the site deploys itself.

  • 5 pull requests merged
  • 0 commits straight to main
  • check: required
  • deploy: GitHub Actions

I'm Rajan. I wrote software for a living before I taught. I now teach programming to secondary students. This is my answer to the module brief. It has a template repository, pull requests, automatic deploys and a class guide.

My students will one day work on a team that guards its main branch. So I set the repository up the way a real team does. A script checks every pull request. A ruleset blocks the merge until the check is green and a teammate approves.

01 The four deliverables

  • Template repositorystall-board-templateEvery file, the set-up steps, and a zip to upload as your own template.
  • Live siteStall BoardThe site as the team left it after the last merge. Try the search box.
  • Merged pull requests5 pull requests, #6 to #10Each with its diff, its check runs and its review. Two went red first.
  • Class guide1-page guide with team rulesFor a Sec 3 class of 32 in 8 teams. Prints on one A4 page.

The pilot team, their account names and the canteen menus are made up, like me. The Git history is real. I made it by running every branch, commit, conflict and merge in Git. The diffs and check logs on these pages come straight from that history.

02 How a change reaches the live site

Each student owns one stall page. A change takes the same path every time.

The workflow file has two jobs. The check job runs node tools/check-site.mjs on every pull request and every push to main. The deploy job runs only on main, and only after check passes. I started from GitHub's "Static HTML" starter workflow. Then I added the check job in front. You can read the whole file on the template page.

The check needs nothing installed. GitHub's Ubuntu runners already come with Node.js. It fails a pull request when:

  • a page has no title, or more or fewer than one main heading;
  • a link points to a file that isn't there;
  • a stall page has no menu with prices;
  • any file looks like it holds a key, password or token;
  • any file has an email address in it;
  • a .env file has been committed.

The last three cover the rubric line on keys and personal data. A script can't catch every leak. It catches the common ones before a human has to.

    04 The ruleset I set on main
    

    

    Rulesets are free on public repositories with GitHub Free. On a private repository they need a paid plan. The team repositories are public anyway. GitHub Pages on a free account needs that.
    

      
  
    • Require a pull request before merging, with 1 required approval. A pull request author can't approve their own, so a teammate has to look.
      • 
  
    • Require status checks to pass before merging, with check added. A red check greys out the merge.
      • 
  
    • Block force pushes and Restrict deletions. Both are on by default. Nobody can rewrite or delete main.
      • 

    

    I leave myself, the admin, out of the bypass list. If I can skip the rules, I will, the day the bell is about to ring. Then my students learn that the rules are for show.
    

    The template page on GitHub's docs doesn't say rulesets are copied to a new repository. So my guide sets the ruleset on each team copy. It takes about two minutes a team.

    06 What I would change
    

    

    I set this up the way I would for a team of engineers. My pilot team showed me that was too much for a first try. In the first session, three of the four spent 20 minutes on branches. They kept editing main in github.dev and couldn't see why the push was refused. The gate did its job. But nobody had shown them the branch picker first. I had skipped that step because it felt obvious to me.
    

    So the guide now has a 10-minute demo of a single change on the projector. It comes before anyone starts their own page. I would also turn on the check in lesson 1. The approval rule can wait until lesson 2.
    

    Two smaller gaps. The fake key in #9 was squash-merged away, so it is not on main. It is still in the commits of the add-mixed-rice branch on GitHub. If it had been a real key, deleting the line would not have been enough. It would have to be cancelled at the service that issued it. And the check only reads code. It can't tell if a page looks broken on a phone. A teammate still has to open the preview.
