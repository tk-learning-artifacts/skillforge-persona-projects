Class LibraryA book loans app in Flask and SQLite, with logins. By Rajan Pillai.

Students sign up, borrow books and return them. The librarian adds books and sees what is overdue. Under it sits a small JSON API, three tables and a 225-line app.py.

I wrote software for a living before I taught. Now I teach programming to secondary students. This is my end project for Backends and Databases. My Sec 3 class builds a cut-down version in three lessons.

          Try to break it

          A backend is only as good as what it refuses. Try these, and read the inspector each time.

          1. Log in with the username ' OR 1=1 -- and any password. You get 401. The inspector shows the text went into the ? as plain data. It never became part of the SQL.
          2. Sign up two users with the same password. Open the users table. The two hashes differ, because each one has its own random salt.
          3. Log in as yourself, then send GET /api/overdue by hand. You get 403. Hiding a button is not security. The server checks.
          4. Send POST /api/loans with {"book_id": 1}. Animal Farm is already out, so you get 409. The database itself refuses the second open loan. See the unique index in schema.sql.
          5. Send GET /api/books/99. You get 404, and a JSON error the page can show.

          One click, step by step

          Here is what happens when a logged-in student clicks Borrow on The Hobbit.

          1. The page calls fetch("/api/loans") with the method POST and the body {"book_id": 2}. The browser adds the session cookie by itself.
          2. Flask matches the path and method to borrow(). It reads the user id from the signed session cookie, then looks the user up.
          3. It checks book 2 exists. Then it runs one INSERT, with the user id and book id bound to the two ? marks. The due date is today in Singapore plus 14 days.
          4. If the book is already out, the unique index makes the INSERT fail. Flask turns that into 409. If not, the with db(): block commits the row.
          5. Flask sends back 201 and the new loan as JSON. The page shows the due date, then asks for the book list again.

          Step 3 is the one students cannot see. That is why the database view is next to the app. You watch the row appear.

          What I would change

          Login has no limit on attempts. Anyone can try passwords all day, and the slow hash is the only brake. A real school app needs a lockout or a delay after a few misses. I left it out to keep login() short enough to teach.

          The twin is also a twin, not the thing itself. It hashes with PBKDF2, because browsers have no scrypt. The code page lists every difference.

          And one lesson note. My first try at lesson 2 asked for three routes in 35 minutes. About half the class finished one. I now give the GET routes in the starter file. Students write only the POST.
