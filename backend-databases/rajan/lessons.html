Build a library APIThree 60-minute lessons for a Sec 3 class that already writes Python.

Students query a library database, write a Flask route that saves a loan, then add hashed logins. Everything runs on the lab PC. All data is made up.

  • Class: 30 Sec 3 students. They have had a year of Python: functions, lists and dictionaries.
  • Time: 3 lessons of 60 minutes, one a week, in the computer lab.
  • Devices: one lab PC each, running Python 3.12 or newer with Flask installed. I ask IT for this two weeks ahead. Flask brings Werkzeug with it.
  • Why the lab, not Chromebooks: Flask needs Python running on the machine. Our school's managed Chromebooks can't install it.
  • Why no hosting accounts: PythonAnywhere's terms (clause 5.2) ask users to be old enough to sign a binding contract. In Singapore that age is 18. So students run their apps on their own PC, at http://127.0.0.1:5000. Only my app goes online, on my account.
  • Starter folder on the shared drive: schema.sql, setup_db.py, the page, and an app.py with the GET routes done. The POST routes are stubs.

By the end, students can

  • Say what the browser sends, what the server does and what the database stores, for one click.
  • Write SELECT, INSERT and JOIN queries on the library tables.
  • Write a Flask route that saves data with ? placeholders.
  • Store passwords as hashes, and say what a leaked table gives away.

Success criteria

  1. Borrowing a book in my page adds one row to loans.
  2. Every value in every query goes in through a ?.
  3. The users table holds hashes, and logging in still works.
  4. The data passes all five data rules below.

Lesson 1: Requests and tables

  1. 0 to 5 Settle, log in. Open Class Library on this site.
  2. 5 to 15 I borrow and return a book on the projector. Students copy on their PC and watch the inspector. They write down 3 status codes they saw and what each meant.
  3. 15 to 20 Mini lesson. Request, response, database. Method and path. Why a server checks, even when the page hides a button.
  4. 20 to 45 SQL. Students run python setup_db.py, then python -m sqlite3 library.db. Cards on the desk ask for five queries. All books by title. One book by id. An INSERT for a new book. A JOIN of loans with books and users. Then only overdue loans, using date('now', '+8 hours').
  5. 45 to 55 Exit task. Write the JOIN that lists who has which book. Hand it in on paper.
  6. 55 to 60 Log off, pack up.

Check: 5 + 10 + 5 + 25 + 10 + 5 = 60 minutes.

Watch for: students who type the SQL without the final semicolon and think the shell is frozen. Tell them up front.

Lesson 2: A route that saves

  1. 0 to 5 Settle. Copy the starter folder to the desktop.
  2. 5 to 15 Demo. I run flask --app app run --debug and open 127.0.0.1:5000. I walk through list_books(): route, query, list of dictionaries, JSON.
  3. 15 to 22 Injection demo, on my PC only. The starter has a route I wrote badly on purpose, with an f-string. I type ' OR 1=1 -- and every row comes back. Then I fix it with ? and type it again.
  4. 22 to 47 Build. Students fill in the borrow() stub. Steps on the board: log in check, read the book id, check the book exists, INSERT with two ? marks, return 201.
  5. 47 to 54 Pair check. Swap seats. Read your partner's app.py and tick each query that uses ? for every value. Borrow a book in their page and find the new row.
  6. 54 to 60 Save the folder to the shared drive. Pack up.

Check: 5 + 10 + 7 + 25 + 7 + 6 = 60 minutes.

Stuck: they use my finished borrow() with three lines blanked out. Early finishers: write give_back(), so a student can only return their own loan.

Lesson 3: Logins and data rules

  1. 0 to 5 Settle. Open the folder from the shared drive.
  2. 5 to 13 Demo in the Python shell. generate_password_hash("test-cat"), twice. Two different strings. Then check_password_hash says yes to both.
  3. 13 to 35 Build. Fill in signup() and login(). Test with two made-up accounts.
  4. 35 to 45 Leak drill. Swap library.db files with your partner. Open their users table. Write 3 sentences: what would an attacker get from this file? What would they get if it stored plain passwords?
  5. 45 to 55 Data rules check. Students run the five checks below on their own folder and fix what fails. They write the README lines the rules ask for.
  6. 55 to 60 Save to the shared drive. Exit line: which rule did you break first, and how did you find out?

Check: 5 + 8 + 22 + 10 + 10 + 5 = 60 minutes.

Data rules, and how I check each one

These go on the first slide of lesson 1 and on the wall. I mark them from the folder on the shared drive.

  1. Made-up data only. Usernames are handles like reader_kite. No real names, classes, NRIC numbers or photos. Check: I open library.db with python -m sqlite3 and read every row of users.
  2. Passwords are hashed. Check: SELECT pw_hash FROM users. Every value starts with scrypt: or pbkdf2:. One plain password and the rule fails.
  3. Test passwords are made up and start with "test-". Students list their test logins in README.txt. Check: I log in with one of them. If a listed password looks like a real one, we talk about it.
  4. Every value goes in through a ?. Check: I search app.py for execute( and read each query. An f-string or a + that carries a request value fails the rule. My fixed TODAY text is the only allowed f-string.
  5. Store only what the app needs. Each column gets a one-line reason in README.txt. Check: I hold schema.sql next to the README. A column with no reason fails. Most students try to add an email column. It has no use here.

How I mark it

Each success criterion gets "yes", "nearly" or "not yet", with one line of comment. Criterion 2 matters most. A joined string with a request value in it is "not yet". That holds even if the app works.
