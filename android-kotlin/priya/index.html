Word Wall

A glossary app for a 6-week app-building course. Students search the 18 words the course uses, open one, and save it for revision. Then they build their own copy from a starter.

I'm Priya. I plan courses for a team of trainers. My question for this module was not "what app would I build?" It was "what app can four trainers run the same way, in three schools with different devices?"

So the app is about the course itself. Every word in it is one students meet in a given week: Event in week 1, LazyColumn in week 5. When students build Word Wall in week 5, they are writing the glossary of what they have just learnt.

  • Sec 3an elective for 4 classes
  • 6 weeksone 60-minute lesson a week
  • 3 schoolsMac lab, Windows laptops, Chromebooks
  • 4 trainersone shared plan

The schools, classes and team are made up for this example, like me. The code is real and builds.

How it works



  

    
State lives in the parent

    
Both screens need search and saved, so WordWallApp holds them. This is state hoisting.


var search by rememberSaveable { mutableStateOf("") }
var saved by rememberSaveable(stateSaver = IdSetSaver) {
    mutableStateOf(emptySet<Int>())
}

  

  

    
State goes down, events go up

    
The list screen gets the text. When you type, it sends the new text back up. It never changes search itself.


OutlinedTextField(
    value = search,
    onValueChange = onSearchChange,
    label = { Text("Search words") }
)

  

  

    
A grouped LazyColumn


val shown = words.filter {
    it.word.contains(search.trim(), ignoreCase = true)
}
LazyColumn {
    shown.groupBy { it.week }.forEach { (week, list) ->
        stickyHeader { Text(weekTitles.getValue(week)) }
        items(list, key = { it.id }) { WordRow(it) }
    }
}

    
The filter runs again on each recomposition. For 18 words that is fine.

  

  

    
Two routes


@Serializable object ListScreen
@Serializable data class WordScreen(val id: Int)

composable<WordScreen> { entry ->
    val id = entry.toRoute<WordScreen>().id
    ...
}

    
Type-safe routes need Navigation 2.8.0 or later and the Kotlin Serialization plugin.

Versions, so four trainers get the same thing

  
Android Gradle Plugin 9.4.1, Kotlin 2.4.21, Compose BOM 2026.09.00, Navigation Compose 2.10.2. It compiles against API 37, with minSdk 24 (Android 7.0). I built it with ./gradlew assembleDebug: no errors, no warnings. Studio may offer upgrades. The team says no until the course ends.

Device plan


One app, three routes. School A runs Studio with the emulator on a Mac lab. School B runs Studio on 8 GB Windows laptops with loan phones. School C has 4 GB Chromebooks, so half the class pairs on a laptop trolley and half builds the App Inventor version. Read the device plan, with the checks against Google's specs, what each group hands in, and why no student app goes on Google Play.

What I would change


I have planned this for four classes, but I have not taught week 5 myself. The 60-minute plan assumes Studio is open and synced at minute 5. In School B, on 8 GB laptops, I doubt it. The first trainer to run it should time the start-up and tell the team. We may need to split week 5 over two lessons.


Saved words are lost when the app is closed. rememberSaveable covers rotation, not a full close. Keeping them would need DataStore, from Unit 6 of Android Basics. That is beyond this course.
